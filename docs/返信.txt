結論

最初に、判断を明確にします。

1. 【確認済み】CUDA 12.3 runtime + CUDA 13.3対応driver + RTX 5090という組み合わせ自体は、非対応ではありません。
    NVIDIAドライバには後方互換性があり、JAXのCUDA 12 wheelも十分に新しいドライバ上で動作する前提です。したがって、「ドライバがCUDA 13.3だからCUDA 12.3 runtimeが止まる」という説明は弱いです。 
2. 【確認済み】JAX 0.5.3 / jaxlib 0.5.3は、Python 3.12上のMuJoCo 3.11.0公式ロックと一致しています。
    少なくとも「JAX 0.5.3だからMuJoCo 3.11.0では非対応」という話ではありません。 
3. 【確認済み】現在のNumPy 2.5.1は、MuJoCo 3.11.0のPython 3.12向け公式ロックであるNumPy 2.1.3から外れています。
    ただし、これがGPUコンパイル／実行停止の直接原因である可能性は低いです。環境が公式再現構成ではないという意味では重要ですが、第一容疑者ではありません。 
4. 【有力仮説】本件は「CUDA 12対13」そのものより、BlackwellでのJAX/XLAコード生成・モジュールロード・PTX JIT・実際にロードされたCUDAライブラリの組み合わせに起因している可能性が高いです。
5. 【未確認】v23の停止点はXLAコンパイルではありません。
    v23ではB=1とB=2のcompile完了ログまで出ています。したがって、その実行について「XLA compile hang」と呼ぶのは事実と矛盾します。候補は次のいずれかです。
    * コンパイル済み実行ファイルのロード
    * GPUへの初回dispatch
    * PTXからcubinへのdriver JIT
    * block_until_ready()相当の同期
    * device_get
    * 比較処理
    * JSONシリアライズ
    * ログに出ていない別shape／別関数の追加コンパイル

JAXは非同期dispatchを行うため、Python関数が返っていてもGPU実行が完了しているとは限りません。明示的にblock_until_ready()またはホスト読み出しを挟まない限り、停止点を確定できません。 

あなたが今もっとも避けるべき誤りは、compileログの直後で止まったから、コンパイラが止まったと決め打ちすることです。現状のログ粒度では根本原因を局所化できていません。

⸻

1. 既知の非推奨・非対応・既知不具合

1.1 CUDA 12.3 runtimeと610系ドライバ

【確認済み】正式な非対応ではありません。

JAXのCUDA 12 wheelはCUDA 12.3でビルドされ、CUDA 12.1以降をサポートする構成です。必要な最低ドライバより610系ドライバは十分に新しいです。また、NVIDIAは新しいドライバで古いCUDA Toolkit向けにビルドされたアプリケーションを動かす後方互換性を提供しています。 

ただし、JAX公式ではWSL2上のNVIDIA GPUをExperimental扱いにしています。これは「動作しない」という意味ではありませんが、Linuxネイティブと同等の保証範囲ではないということです。 

判定は次のとおりです。

項目	判定
CUDA 12.3 runtimeをCUDA 13.3対応driverで動かす	対応範囲
RTX 5090でCUDA 12系wheelを動かす	原理上対応
WSL2上のJAX GPU	JAX公式ではExperimental
この組み合わせだけを原因と断定	根拠不足

1.2 RTX 5090／BlackwellとCUDA 12

【確認済み】RTX 5090 Laptop GPUはBlackwell世代です。 

CUDA 12.8は、Blackwell向けのsm_100、sm_101、sm_120をコンパイラで正式に扱う最初のCUDA 12系リリースです。CUDA 12.8以前にビルドされたコードでも、適切なPTXが含まれていれば、ドライバがBlackwell向けcubinへJITコンパイルして動作できます。 

ここで重要なのは、あなたの表示している「JAX runtime CUDA 12.3」だけでは、次が分からないことです。

* 実際のptxasバージョン
* nvidia-cuda-nvcc-cu12
* nvidia-cuda-runtime-cu12
* cuBLAS、cuDNN、cuSolver、cuSparse等の実バージョン
* wheel内またはpip依存のどのライブラリがロードされたか
* LD_LIBRARY_PATHによってシステム側ライブラリに差し替わっていないか
* native sm_120 cubinを使っているのか、PTX JITなのか

JAX 0.5.3のCUDA依存には、すべてを一点固定するのではなく下限指定になっているものがあります。したがって、jax、jaxlib、plugin、pjrtが0.5.3で揃っていても、CUDA関連の推移依存全体が同一の既知構成である保証はありません。 

これは現状でもっとも大きな盲点です。

1.3 MuJoCo 3.11.0とJAX 0.5.3

【確認済み】この組み合わせはMuJoCo側の公式ロックに含まれています。

MuJoCo 3.11.0のロックは概ね次の構成です。

Python	JAX / jaxlib	CUDA plugin / pjrt	NumPy
< 3.13	0.5.3	0.5.3	2.1.3
>= 3.13	0.8.3	0.8.3	2.4.4

したがって、現在のJAX 0.5.3は非対応ではありません。ただし、NumPy 2.5.1とCUDA推移依存を含め、環境全体は公式ロックの完全再現ではありません。

また、mujoco-mjx==3.11.0自体はJAXを狭く固定しておらず、Python 3.10以降をサポートしています。 

1.4 Blackwellで報告されているJAX/XLA問題

以下は一次情報上、関連性があります。ただし、本件と同一症状ではありません。

RTX 5090＋同じ610.43.02ドライバでXid 31

【確認済み】 RTX 5090、ドライバ610.43.02、CUDA 13.3、JAX 0.10.1付近で、約20個の異なるJITコンパイル後にGPU Xid 31が発生する未解決報告があります。 

本件との違い

* あなたのテストは約3コンパイルです。
* 現時点でXid 31は確認されていません。
* 問題側はCUDA 13 plugin/JAX 0.10.1で、あなたはCUDA 12/JAX 0.5.3です。

したがって、Blackwell＋610系ドライバに問題が存在し得る証拠ではありますが、本件の直接証拠ではありません。

RTX 5090でのdelay-kernel timer警告

OpenXLAには、RTX 5090でクロック周波数の仮定が不適切なためタイマー警告や遅延が発生する報告があります。しかし、報告者はPTX JITとnative sm_120双方を比較し、PTX JIT自体を原因から外しています。これは主に性能測定系の問題であり、今回の数分間停止とは一致しません。 

sm_120でのsilent miscompile

JAX 0.10.2ではRTX 5090上の特定のGEMM融合で、デフォルトautotuneによるsilent miscompileの報告があります。 

これは停止ではありません。ただし、あなたの「ビット単位で厳密評価する」という要件にとって重要です。
autotuneレベルやTriton GEMM等のXLAフラグを変えて通す方法は、結果を変え得るため復旧策として採用してはいけません。

1.5 MJX 3.11.0固有の同一hang

【未確認】

一次情報を確認した範囲では、次の完全一致報告は見つかっていません。

* RTX 5090
* WSL2
* MJX 3.11.0
* JAX 0.5.3
* B=1／B=2のmjx.step
* compile完了後またはcompile途中でGPU利用率0%のまま停止

MuJoCo 3.11.0の公式changelogにも、これと明確に一致する修正項目はありませんでした。これは「バグではない」という意味ではなく、既知問題として特定できていないという意味です。 

⸻

2. 「CUDA 12.3 runtime + CUDA 13.3 driver + RTX 5090」は有力原因か

確認済みの事実

* 新しいドライバで古いCUDA runtimeを動かすことはNVIDIAの対応範囲です。 
* JAX CUDA 12 wheelの使用条件上、610系ドライバは十分に新しいです。 
* Blackwell native code生成はCUDA 12.8以降で本格対応します。 
* それ以前のtoolkitで生成されたPTXも、適切なPTXが含まれていればdriver JITで動作できます。 
* JAXの4パッケージが0.5.3でも、実際のnvidia-*依存やロードライブラリは未確定です。 

有力仮説

もっとも妥当なのは、以下の複合要因です。

Blackwell上で、JAX/XLA 0.5.3が生成したプログラムを、実際にインストールされたCUDA 12系ライブラリと610系ドライバがロード／JIT／実行する経路のどこかで停止している。

つまり、

* 「CUDA 12.3だから駄目」
* 「CUDA 13.3ドライバだから駄目」
* 「RTX 5090だから駄目」

のどれか単独ではなく、特定バージョン間の相互作用が有力です。

また、v24だけcompile完了ログが出なかった理由として、persistent cache、CUDA compute cache、compile順序、shape特殊化、ホストメモリ状態などの差も考えられます。

未確認

現時点では以下が欠けています。

* .lower()の終了時刻
* .compile()の終了時刻
* compiled executable呼び出しが返ったか
* 最初のGPU同期が返ったか
* device_getが返ったか
* CUDA module load／PTX JITが発生したか
* GPU Xidが発生していないか
* 実際にロードされたlibcuda、libcudart、cuBLAS等
* Pythonスレッドが何を実行または待機しているか

したがって、現段階での評価は次です。

仮説	評価
CUDA 12 runtimeをCUDA 13 driverで動かしていること自体	原因として弱い
Blackwell＋古めのJAX/XLAコード生成経路	有力
pip内CUDA依存とシステムCUDAの混在	有力、未確認
PTX JIT／module load／CUDA cache	有力、未確認
WSL2＋610系driver固有問題	中程度。Xid確認前は断定不可
MuJoCoとMJXのバージョン不一致	否定済み
NumPy 2.5.1単独	低いが除去すべきノイズ
PPOやOpenDuck環境コード	上流mjx.stepまで切り出しているため優先度低

⸻

また、同じvenv内でCUDA 12 pluginをCUDA 13 pluginに差し替えるのも禁止です。残存ファイルや依存解決差が入り、比較不能になります。

import faulthandler
import hashlib
import json
import signal

import jax

faulthandler.register(signal.SIGUSR1, all_threads=True, chain=False)
faulthandler.dump_traceback_later(60, repeat=True)
def emit(stage: str, **fields: Any) -> None:
    record = {
        "stage": stage,
        "monotonic_ns": time.monotonic_ns(),
        **fields,
    }
    print(json.dumps(record, sort_keys=True, default=str), flush=True)
def sync_tree(tree: Any) -> None:
    """Wait for every JAX output buffer."""
    for leaf in tree_util.tree_leaves(tree):
        block = getattr(leaf, "block_until_ready", None)
        if block is not None:
            block()
def compile_executable(
    label: str,
    jitted_fn: Any,
    *args: Any,
) -> Any:
    emit(f"{label}.lower.start")
    lowered = jitted_fn.lower(*args)
    emit(f"{label}.lower.done")
    emit(f"{label}.compile.start")
    executable = lowered.compile()
    emit(f"{label}.compile.done")
    return executable
def execute_executable(
    label: str,
    executable: Any,
    *args: Any,
) -> Any:
    emit(f"{label}.execute.call")
    result = executable(*args)
    emit(f"{label}.dispatch.returned")
    emit(f"{label}.block.start")
    sync_tree(result)
    emit(f"{label}.block.done")
    emit(f"{label}.device_get.start")
    host_result = jax.device_get(result)
    emit(f"{label}.device_get.done")
    return host_result
def _array_bytes(value: Any) -> tuple[tuple[int, ...], str, bytes] | None:
    if isinstance(value, (np.ndarray, np.generic, bool, int, float, complex)):
        array = np.ascontiguousarray(np.asarray(value))
        return array.shape, array.dtype.str, array.tobytes(order="C")
    return None
def exact_tree_report(left: Any, right: Any) -> dict[str, Any]:
    left_items, left_def = tree_util.tree_flatten_with_path(left)
    right_items, right_def = tree_util.tree_flatten_with_path(right)
    mismatches: list[dict[str, Any]] = []
    digest = hashlib.sha256()
    if left_def != right_def:
        return {
            "equal": False,
            "reason": "pytree_definition_mismatch",
            "left_def": str(left_def),
            "right_def": str(right_def),
        }
    for (left_path, left_value), (right_path, right_value) in zip(
        left_items,
        right_items,
        strict=True,
    ):
        path = tree_util.keystr(left_path)
        left_array = _array_bytes(left_value)
        right_array = _array_bytes(right_value)
        if left_array is not None and right_array is not None:
            left_shape, left_dtype, left_bytes = left_array
            right_shape, right_dtype, right_bytes = right_array
            digest.update(path.encode())
            digest.update(str(left_shape).encode())
            digest.update(left_dtype.encode())
            digest.update(left_bytes)
            if (
                left_shape != right_shape
                or left_dtype != right_dtype
                or left_bytes != right_bytes
            ):
                mismatches.append(
                    {
                        "path": path,
                        "left_shape": left_shape,
                        "right_shape": right_shape,
                        "left_dtype": left_dtype,
                        "right_dtype": right_dtype,
                        "left_sha256": hashlib.sha256(left_bytes).hexdigest(),
                        "right_sha256": hashlib.sha256(right_bytes).hexdigest(),
                    }
                )
        elif repr(left_value) != repr(right_value):
            mismatches.append(
                {
                    "path": path,
                    "left": repr(left_value),
                    "right": repr(right_value),
                }
            )
    return {
        "equal": not mismatches,
        "left_tree_sha256": digest.hexdigest(),
        "mismatch_count": len(mismatches),
        "mismatches": mismatches[:20],
    }
def build_rollout(model: Any) -> Any:
    def rollout(data: Any, ctrl: Any) -> Any:
        def substep(_: int, state: Any) -> Any:
            state = state.replace(ctrl=ctrl)
            return mjx.step(model, state)
        return lax.fori_loop(0, 10, substep, data)
    return jax.jit(rollout)
def run_strict_probe(
    model: Any,
    data_b1: Any,
    ctrl_b1: Any,
    data_b2: Any,
    ctrl_b2: Any,
    take_lane1_from_host_b2: Callable[[Any], Any],
    compile_order: tuple[str, str] = ("B1", "B2"),
) -> dict[str, Any]:
    emit(
        "environment",
        jax_version=jax.__version__,
        backend=jax.default_backend(),
        devices=[str(device) for device in jax.devices()],
        compile_order=compile_order,
    )
    rollout = build_rollout(model)
    inputs = {
        "B1": (data_b1, ctrl_b1),
        "B2": (data_b2, ctrl_b2),
    }
    executables: dict[str, Any] = {}
    for label in compile_order:
        executables[label] = compile_executable(
            label,
            rollout,
            *inputs[label],
        )
    b1_first = execute_executable(
        "B1.first",
        executables["B1"],
        *inputs["B1"],
    )
    b1_second = execute_executable(
        "B1.second",
        executables["B1"],
        *inputs["B1"],
    )
    b2_first = execute_executable(
        "B2.first",
        executables["B2"],
        *inputs["B2"],
    )
    b2_second = execute_executable(
        "B2.second",
        executables["B2"],
        *inputs["B2"],
    )
    reports = {
        "B1_repeat": exact_tree_report(b1_first, b1_second),
        "B2_repeat": exact_tree_report(b2_first, b2_second),
        "B1_vs_B2_lane1": exact_tree_report(
            b1_first,
            take_lane1_from_host_b2(b2_first),
        ),
    }
    final = {
        "status": (
            "PASS"
            if all(report["equal"] for report in reports.values())
            else "FAIL"
        ),
        "reports": reports,
    }
    emit("result", result=final)
    return final

呼び出し上の注意

take_lane1_from_host_b2には、あなたが現在使っている検証済みlane抽出関数を渡してください。

安易に、

x[1:2] if x.shape[0] == 2 else x

だけで全pytreeを処理すると、batch次元ではない先頭長2の構造フィールドまで切る危険があります。ここを雑に処理すると、比較試験そのものが壊れます。

"""
host_model = mujoco.MjModel.from_xml_string(XML)
model = mjx.put_model(host_model)
def make_one(z: jax.Array):
    data = mjx.make_data(model)
    return data.replace(qpos=data.qpos.at[2].set(z))
data_b2 = jax.vmap(make_one)(
    jnp.asarray([0.060, 0.055], dtype=jnp.float32)
)
def verified_device_lane1(tree):
    # この最小モデル専用。OpenDuckでは既存の検証済みselectorを使うこと。
    return jax.tree.map(
        lambda x: (
            x[1:2]
            if isinstance(x, jax.Array)
            and x.ndim > 0
            and x.shape[0] == 2
            else x
        ),
        tree,
    )
data_b1 = verified_device_lane1(data_b2)
ctrl_b2 = jnp.zeros((2, host_model.nu), dtype=jnp.float32)
ctrl_b1 = ctrl_b2[1:2]
def verified_host_lane1(tree):
    return jax.tree.map(
        lambda x: (
            x[1:2]
            if isinstance(x, np.ndarray)
            and x.ndim > 0
            and x.shape[0] == 2
            else x
        ),
        tree,
    )
run_strict_probe(
    model=model,
    data_b1=data_b1,
    ctrl_b1=ctrl_b1,
    data_b2=data_b2,
    ctrl_b2=ctrl_b2,
    take_lane1_from_host_b2=verified_host_lane1,
)

実行時の隔離設定

各venv・各runごとに独立したcacheディレクトリを作ります。

RUN_ROOT="$PWD/diagnostics/$(date +%Y%m%d-%H%M%S)"
mkdir -p "$RUN_ROOT/jax-cache" "$RUN_ROOT/cuda-cache"
env \
  -u XLA_FLAGS \
  -u LD_LIBRARY_PATH \
  JAX_PLATFORM_NAME=gpu \
  JAX_LOG_COMPILES=1 \
  JAX_COMPILATION_CACHE_DIR="$RUN_ROOT/jax-cache" \
  CUDA_CACHE_PATH="$RUN_ROOT/cuda-cache" \
  timeout \
    --signal=USR1 \
    --kill-after=30s \
    600s \
  python -u strict_mjx_probe.py \
  >"$RUN_ROOT/stdout.log" \
  2>"$RUN_ROOT/stderr.log"
echo "$?" >"$RUN_ROOT/exit_code.txt"

LD_LIBRARY_PATHを外すのは、JAX pip wheelが意図したCUDAライブラリではなく、WSL内の別CUDAライブラリを拾う事態を防ぐためです。JAX公式もLD_LIBRARY_PATHによるCUDA library overrideに注意を促しています。 

ただし、これはpip CUDA wheelを使用する隔離venvでのみ行ってください。

合格条件

単に1回JSONが出れば合格ではありません。

各venvで最低限、次を満たす必要があります。

1. 同じcompiled B=1 executableを2回実行し、bitwise一致
2. 同じcompiled B=2 executableを2回実行し、bitwise一致
3. B=1とB=2 lane 1がbitwise一致
4. fresh processで3回一致
5. B=1→B=2 compile順で一致
6. B=2→B=1 compile順でも一致
7. 空のJAX／CUDA cacheからのcold runで一致
8. 同一cacheを使ったwarm runでも一致
9. tiny MJXとOpenDuck canonicalの両方で一致
10. すべてGPU backendで実行

B=1とB=2はshapeが違うため、XLA上は別プログラムです。したがってcross-shape bitwise equalityはJAX一般の保証ではなく、あなたが設定した追加の受け入れ条件です。

これは問題ありません。
ただし、失敗した場合は「誤差が小さいから採用」ではなく、そのstackはあなたの要件に不適合として棄却すべきです。

⸻

5. Persistent compilation cache、XLA_FLAGS、CUDA pluginの扱い

5.1 JAX persistent compilation cache

JAXのpersistent cache keyには、HLO、jaxlibバージョン、関連XLA flags、device configurationなどが含まれます。 

安全な扱いは次です。

採用する扱い

* venvごとに別cacheディレクトリ
* CUDA 12／CUDA 13で別cache
* JAX 0.5.3／0.8.3で別cache
* XLA flags変更ごとに別cache
* 最初の検証は空cache
* cold run合格後に同一cacheでwarm run
* cacheディレクトリとmanifestをrun artifactに保存

採用しない扱い

* 既存の全体cacheを削除して現環境まで巻き込む
* 異なるvenvで同じcacheを共有
* warm cacheで通ったから直ったと判断
* driver更新前後で同じcacheを使う

JAXの公開されたcache key構成にdriver versionが必ず含まれるとは限りません。したがって、driver変更前後でcacheを共有するのは危険です。これは公開仕様からの保守的推論です。 

5.2 CUDA compute cache

NVIDIA driver側にもPTX JIT結果等を保存するCUDA cacheがあります。

安全な設定は、

CUDA_CACHE_PATH="$RUN_ROOT/cuda-cache"

としてrunごとに隔離することです。NVIDIAはCUDA_CACHE_PATH、CUDA_CACHE_DISABLE、CUDA_FORCE_PTX_JIT等を公式に提供しています。 

CUDA_CACHE_DISABLE=1は診断用です。通常運用の解決策にはしません。

5.3 CUDA_FORCE_PTX_JIT=1

これはBlackwell互換性確認のための一回限りの診断です。

CUDA_FORCE_PTX_JIT=1 \
CUDA_CACHE_PATH="$RUN_ROOT/cuda-cache-ptx" \
python -u strict_mjx_probe.py

意味は次のとおりです。

* 通る
    → PTXが含まれ、driver JIT経路が少なくとも動く
* 明確な互換性エラーになる
    → 必要なPTXが含まれていない可能性
* 同じ場所で止まる
    → PTX JIT経路を含むmodule load／driver側を疑う

ただし、これを恒久設定にしてはいけません。
検証後は必ずunsetします。NVIDIAも互換性検査後に解除するよう説明しています。 

逆に、

CUDA_DISABLE_PTX_JIT=1

を使えばnative cubinだけで動作可能か確認できます。これも診断専用です。

5.4 XLA_FLAGS

ベースラインでは、

env -u XLA_FLAGS

にしてください。

特に次のような設定を「通すための修正」に使ってはいけません。

* GEMM autotune level変更
* Triton GEMMの有効化／無効化
* fusionの変更
* fast-math関連
    -演算再結合関連
* deterministic operation関連
* TF32経路変更
* latency hiding scheduler変更
* compiler optimization level変更

これらは生成kernelや演算順を変え、物理状態のbit列を変える可能性があります。

診断用として許されるのは、例えば次です。

XLA_FLAGS="--xla_dump_to=$RUN_ROOT/xla-dump"

これはHLOや生成物を保存するための観測設定です。ただし、設定値は必ずmanifestへ残してください。

5.5 CUDA_LAUNCH_BLOCKING=1

CUDA_LAUNCH_BLOCKING=1

は非同期実行の停止点を特定する診断として有効です。

ただし、最終合格試験はこの設定なしで行います。スケジューリングを変えた状態だけで通っても、通常運用の再現性が確認されたことにはなりません。

5.6 CUDA plugin更新

pluginだけ更新してはいけません。

次を一単位として、新しいvenvでまとめて変更します。

* jax
* jaxlib
* jax-cudaXX-plugin
* jax-cudaXX-pjrt

また、バージョン更新後は生成HLO、lowering、kernel選択が変わり得ます。
したがって、0.5.3と0.8.3の出力hashが一致しないこと自体を不具合とは判定できません。

比較すべきなのは、

* 同一stack内のfresh-process再現性
* 同一stack内のB=1／B=2 lane一致

です。

合格したstackは、次まで固定してください。

python -m pip freeze --all > manifest.lock.txt
python -m pip check > pip-check.txt

可能ならwheelも保存し、SHA-256を記録します。

⸻

6. 採用してはいけない対処

次は復旧ではなく、問題の隠蔽です。

* CPUで通ったので採用
* allcloseの許容差を広げる
* bitwise gateを削除
* B=2検証を削除してB=1だけ使う
* timeoutを無制限に延ばして待つ
* warm cacheで一度通ったので採用
* jax_disable_jit=True
* solver iteration数の変更
* timestepの変更
* contact設定の変更
* OpenDuckモデルの簡略化を最終解決とする
* jax_enable_x64を変更して通す
* XLA autotuneやfusion設定を変更して通す
* MJX-JAXから別実装へ切り替えて同じ物理だと扱う
* 現venvへ上書きインストール
* CUDA 12 pluginとCUDA 13 pluginを同居させる
* いきなりWindows／WSL／GPU driverを更新またはdowngrade
* GPU再現性確認前にPPOを再開

特にdriver変更は最後です。システム全体を動かす破壊的な変数であり、現時点ではdriver原因の証拠が足りません。

非破壊の復旧判断フロー

P0 inventory採取
  |
  +-- CUDA依存混在あり
  |      -> C0で公式ロック再構築
  |
  +-- 混在なし
         -> Gate 1: JAX単体
                |
                +-- hang/fail
                |      -> JAX/XLA・CUDA plugin・driver・WSL層
                |
                +-- pass
                       -> Gate 2: tiny MJX
                              |
                              +-- hang/fail
                              |      -> MJX lowering/contact/solverとXLAの相互作用
                              |
                              +-- pass
                                     -> Gate 3: OpenDuck canonical
                                            |
                                            +-- hang
                                            |      -> OpenDuck model構造、
                                            |         static fields、shape、
                                            |         actuator/control経路
                                            |
                                            +-- bitwise failのみ
                                                   -> shape依存codegen
                                                      としてstack棄却

venvの採用判定は次です。

C0	R1	R2	判断
PASS	未実施	未実施	現venv汚染／依存差が主因
FAIL	PASS	未実施	JAX 0.5.3／旧CUDA 12 build経路が主因候補
FAIL	FAIL	PASS	CUDA 12 plugin経路固有の可能性が高い
FAIL	FAIL	FAIL	driver／WSL2／モデル固有loweringを優先調査
JAX単体から全FAIL	-	-	MuJoCoではなくJAX／CUDA／driver層
JAX単体PASS、tiny MJX FAIL	-	-	MJX/XLA lowering層
tiny MJX PASS、OpenDuckのみFAIL	-	-	OpenDuck model/data/control構造
