# G1を歩行から5m/s安定走行まで発展させた設計プロセス

## 1. 全体像

今回行ったことは、単純に速度指令の上限を少しずつ上げた作業ではありません。

実際には、各段階で方策が陥っている局所解を計測し、その失敗原因に対応する最小限の変更を加えながら、方策を次の運動様式へ移していきました。

大きく分けると、次の5段階です。

```text
安定歩行の獲得
    ↓
高速でも転倒しない歩行への拡張
    ↓
飛行相を伴う周期走行への相転移
    ↓
高速度化に伴う衝撃・飽和・滑りの改善
    ↓
5m/sでの速度・周期・低滑り・低衝撃の同時達成
```

最終的には、Isaac Lab上で5.0m/s指令に対して、

* 平均実速度：4.818m/s
* 50エピソード転倒：0回
* 周期走行成功率：100%
* 定常前進速度誤差：0.075m/s
* 全体滑り：0.348m/s
* 着地衝撃p95：2072N
* 左右膝速度飽和：1.76% / 2.49%
* 左右足首トルク飽和：5.18% / 6.48%

を達成しました。

重要なのは、この結果が一度の報酬設計で出たのではなく、**失敗を分類し、計測し、局所的に修正する反復によって出た**ことです。

# 2. 変えなかった基盤

全Stageを通して、基本的な入出力構造は維持しました。

## 方策の入出力

観測は123次元です。

* base linear velocity
* base angular velocity
* projected gravity
* velocity command
* 37関節の位置
* 37関節の速度
* 直前の37次元action

行動は、G1の37関節に対するposition targetです。

Actorは概ね、

```text
123 → 256 → 128 → 128 → 37
```

Criticは、

```text
123 → 256 → 128 → 128 → 1
```

です。

ネットワークを大きくしたから5m/sへ到達したわけではありません。むしろ、**ネットワーク・観測・行動を固定したまま、学習分布と報酬の意味を段階的に変えた**ことが重要です。

## 速度指令が観測に含まれていた意味

方策は特定速度の動きを暗記するのではなく、

[
a_t = \pi(o_t, v_{\mathrm{cmd}})
]

として、現在状態と指令速度から関節指令を生成します。

この構造によって、方策内部では、

* 速度に応じて歩幅を変える
* ステップ周期を変える
* 接地時間を変える
* 飛行時間を変える
* 前傾や腕振りを変える

という連続的な制御則を学習できます。

このため、学習範囲の上限を超えても、ある程度まで自然に外挿できました。

# 3. ベースライン：公式歩行方策の十分な学習

最初はIsaac Lab公式のG1平地速度追従環境を、そのまま利用しました。

環境は、

```text
Isaac-Velocity-Flat-G1-v0
```

アセットは、

```text
G1_MINIMAL_CFG
```

です。

## 基本報酬

公式の報酬には、次のような項目が含まれていました。

* 前進・横速度の追従
* yaw速度の追従
* 上下方向速度の抑制
* roll・pitch角速度の抑制
* トルク抑制
* 関節加速度抑制
* action変化抑制
* 足のair time
* 上体姿勢維持
* 関節制限
* 足滑り
* 腕・腰・指の姿勢逸脱抑制
* 転倒への大きな罰則

ここで重要なのは、走行専用報酬がなくても、既に以下を学習していたことです。

* 転倒しない
* 上体を垂直に保つ
* 左右の脚を交互に動かす
* 指令速度に追従する
* 接地中の足を過剰に滑らせない
* actionを滑らかにする
* 外乱後に姿勢を戻す

これらは走行にも必要な基礎技能です。

## 学習量

まず約1000 iterations学習し、そのcheckpointからさらに約2000 iterations追加しました。

最終的な歩行checkpointは約2999 iterations学習済みで、

* 平均episode長：約989.6 / 1000
* time-out終了：約95.7%
* 転倒終了：約4.3%
* XY速度誤差：約0.159m/s

でした。

この時点ではまだ高速ではありませんが、**非常に安定した方策の初期点**ができました。

# 4. Stage 1：1.5m/sまでの高速歩行

## 目的

Stage 1の目的は走行ではありません。

> 速度を上げても、既存の歩行安定性を壊さない

ことでした。

## 速度範囲

```text
前進速度：0〜1.5m/s
横速度：±0.1m/s
yaw速度：±0.2rad/s
```

heading targetは無効化し、前進速度追従へ集中させました。

## 報酬変更

主な変更は以下です。

* XY速度追従weight：1.0 → 2.0
* air-time weight：0.75 → 0.25
* air-time threshold：0.4秒 → 0.25秒
* feet-slide penalty：-0.1 → -0.2

### air-time報酬を弱めた理由

最初から「両足が浮く」ことを強く報酬化すると、方策は走るのではなく、前方へ跳んで転倒する可能性があります。

そのためStage 1では飛行相を積極的に作らせず、まず高速でも接地と姿勢を維持させました。

## 結果

概ね、

* 1.0m/s：安定
* 1.5m/s：転倒率0%
* 2.0m/s：不安定

となりました。

Stage 1で獲得したのは、**1.5m/s付近まで崩れない高速歩行**です。

---

# 5. Stage 2：2.2m/sまで高速歩行を拡張

## 目的

Stage 1で得た歩行を保ったまま、さらに速度域を広げました。

速度上限は2.2m/sです。

この段階では報酬を大きく変えず、主に指令速度分布を拡張しました。

## 結果

評価では、

|   指令 |  実速度 | 転倒率 |   飛行相 |   滑り |
| ---: | ---: | --: | ----: | ---: |
|  1.5 | 1.40 |  0% | 約0.3% | 0.25 |
| 1.75 | 1.63 |  0% | 約0.4% | 0.31 |
|  2.0 | 1.86 |  0% | 約0.4% | 0.39 |
|  2.2 | 2.04 |  0% | 約0.5% | 0.46 |

となりました。

これは安定していますが、飛行相はほぼありません。

したがって、

> 2.2m/sまでの高速な速歩き

です。

## ここで発見した問題

2.4〜2.7m/sへ外挿したところ、飛行相が少し増え、一部が従来の分類器で`running`と判定されました。

しかし50エピソードで詳しく見ると、

* 飛行相はごく短い
* 周期的に繰り返されていない
* 高速になるほど滑りと転倒率が増える

という状態でした。

ここで、従来の走行判定が甘すぎることが分かりました。

単に、

* 飛行相割合
* 最大飛行時間

だけを見ると、一度だけジャンプしたエピソードも走行と判定されます。

# 6. Stage 3：走行そのものを定義する

## 速度分布の変更

Stage 3では低速領域をほぼ捨て、走行への遷移帯へ学習を集中させました。

```text
全範囲：2.3〜2.6m/s
70%：2.4〜2.5m/s
30%：2.3〜2.6m/s
```

0〜2.6m/sを一様にサンプリングしなかったことが重要です。

一様分布では、既にできる1m/s前後の歩行へ大量の学習サンプルを浪費します。

## 安全な周期走行報酬

`safe_periodic_flight`を追加しました。

着地時に以下をすべて要求しました。

* 指令速度2.3m/s以上
* 速度誤差0.30m/s以下
* 上体傾斜0.20rad以下
* 鉛直速度絶対値0.50m/s以下
* 飛行時間0.04〜0.16秒
* 片足着地
* 前回と反対側の足への着地

最初の着地は、左右位相の初期化だけに使い、報酬は与えませんでした。

## 新しい走行判定

走行判定も厳格化しました。

`periodic_running`には、少なくとも以下を要求しました。

* 飛行イベント4回以上
* 連続安全周期3回以上
* 左右交互着地率80%以上
* 正常着地率80%以上
* 平均飛行時間0.04〜0.16秒

さらに速度別の走行成功は、80%以上のエピソードが`periodic_running`の場合だけ成立としました。

これにより、

* 単発ジャンプ
* 接触センサーの瞬間的な非接触
* ジャンプ後に転倒
* 同じ足への連続着地

を走行と誤認しなくなりました。

## Stage 3の結果

速度性能は大幅に改善しました。

* 2.3〜2.6m/sで転倒率0%
* 実速度2.21〜2.49m/s
* 滑り0.29〜0.36m/s

しかし、

* 飛行イベントは存在
* 最大連続安全周期は0
* `safe_periodic_flight`報酬発火は0

でした。

つまり、

> 非常に強い高速歩行は学習したが、走行周期への移行には失敗した

という結果です。

# 7. Stage 3の失敗診断：報酬の疎性

ここで報酬係数を適当に上げるのではなく、飛行イベントを分解しました。

106回の飛行イベントの内訳は、

* 20ms：77回
* 40ms：14回
* 60ms：9回
* 80ms以上：6回

でした。

追加の接触履歴解析により、これらはセンサーのチャタリングではなく、実際の短い飛行相であることも確認しました。

40ms以上の有効候補は29回ありましたが、29回すべてが着地時の厳密な速度追従条件を満たしませんでした。

ここで原因が明確になりました。

> 飛行相が存在しないのではなく、飛行相・速度・姿勢・着地・左右交互性を同時に満たすイベントが存在しなかった

のです。

Stage 3の報酬は、完成形にしか報酬を与えませんでした。

PPOから見ると、

* 20ms浮いた
* 姿勢を保った
* 片足へ着地した
* 40ms浮けた

といった中間的な改善はすべて0点です。

これは典型的な疎報酬問題です。

---

# 8. Stage 4：前駆報酬による走行への相転移

Stage 4ではStage 3を残し、走行に近づく途中にも学習信号を与えました。

## 前駆報酬

安全条件を満たした飛行中に報酬を与えます。

* 安全な20ms離地：raw 0.05 / step
* 40〜160msの安全飛行：raw 0.25 / step
* 1イベントあたりraw 0.75で上限
* 160msを超える飛行：raw -0.25 / step

前駆段階では、速度誤差の許容を1.20m/sまで緩めました。

## 着地完了報酬

安全な飛行後に、

* 片足着地
* 前回と反対側の足
* 速度誤差0.30m/s以内

を満たすとraw 2.0を与えました。

つまり、報酬を次の段階へ分解しました。

```text
離地する
  → 小報酬

適切な時間、姿勢を保って飛ぶ
  → 追加報酬

反対側の足へ安全に着地する
  → 完了報酬

周期を繰り返す
  → 反復して報酬
```

## 座標系の修正

速度追従条件も、公式の速度報酬と同じgravity-aligned yaw frameへ揃えました。

異なる座標系で速度条件を判定すると、公式速度報酬では成功している動作が、走行報酬側では失敗扱いされる可能性があります。

## 結果

Stage 4は明確な相転移を起こしました。

2.3〜2.6m/sで、

* 転倒率0%
* 飛行相約31%
* 飛行イベント約125回
* 連続安全周期約120回
* 滑り0.27〜0.29m/s
* `periodic_running`

となりました。

Stage 3では飛行相約1%、連続周期0でした。

Stage 4では、報酬の途中経過を可視化したことで、方策が高速歩行の局所解から周期走行のlimit cycleへ移動しました。

## 予想外の外挿

Stage 4の学習範囲は2.3〜2.6m/sでしたが、その方策は、

* 3.2m/sまで安定
* 3.7m/sまで周期走行
* 3.8m/sで急激に破綻

しました。

これは方策が2.6m/sの固定モーションを暗記したのではなく、**速度指令に応じた歩容変換則**を学習していたことを示唆します。

# 9. Stage 5：3.8m/sの崖を越えて4.0m/sへ

Stage 4は3.7m/sでは安定しましたが、3.8m/sで、

* 転倒率50%
* 滑り0.83m/s
* 実速度低下
* 周期崩壊

が起こりました。

これは徐々に悪化したのではなく、現在の歩容の安定領域を外れた「崖」でした。

## 速度カリキュラム

Stage 5では段階的に上限を上げました。

```text
Stage 0：上限3.8m/s
Stage 1：上限3.9m/s
Stage 2：上限4.0m/s
```

分布は、

* 70%：3.6m/s〜現在上限
* 30%：3.4m/s〜現在上限

です。

高速度を最初から一様に与えず、現在できる領域のすぐ外側を重点的に学習しました。

## 品質gate

単に転倒しなければ昇格するのではなく、以下を要求しました。

* 非転倒
* episode長90%以上
* 安全な左右交互着地3回以上
* 足別滑り0.65m/s以下
* 関節速度上限95%以上の時間5%以下
* 関節トルク上限95%以上の時間20%以下
* 最大着地衝撃3500N以下
* 上体上下動0.30m以下
* stride・contact time左右非対称20%以下

診断termは常に0を返し、報酬そのものは変えませんでした。

これは、**まず高速化だけを学習させ、どの物理量が壊れるかを測るため**です。

## 結果

Stage 5では4.0m/s指令に対して、

* 実速度約3.83m/s
* 転倒率0%
* 滑り約0.50m/s

まで到達しました。

以前は4.0m/sで転倒率83%だったため、大幅な改善です。

一方で、瞬間最大着地衝撃が5000Nを超えるケースや、関節上限への到達が観測されました。

ここで次の課題は、速度ではなく物理品質へ移りました。

# 10. Stage 6：低衝撃化と飽和抑制

## 詳細診断

最大値だけでは意味が不明なので、着地衝撃を分布として計測しました。

4.0m/s付近では、

* 衝撃平均：約1091N
* 中央値：約863N
* p95：約2175N
* p99：約2975N
* 3500N超過率：約0.75%
* 最大値：約5275N

でした。

最大値は大きいものの、ほとんどの着地は品質基準内でした。

左右差を見ると、

* 左足平均：約861N
* 右足平均：約1322N
* 左足p95：約1770N
* 右足p95：約2717N

でした。

さらに、

* 接触直前下降速度：左2.56m/s、右3.29m/s
* 左足首rollトルク飽和：約15%
* 高衝撃イベントの多くが膝速度または足首トルク飽和と同時

でした。

主因は、

> 右足を速く下ろしすぎて強く着地していること
> 左足首rollへ継続的に負荷が偏っていること

です。

## 追加報酬

Stage 6では速度範囲を3.8〜4.0m/sに固定し、以下を追加しました。

### 着地衝撃

15ms平均荷重の1000N超過量に対する二乗hinge。

### 接触前足速度

接触直前下降速度3.0m/s超過量に対する二乗hinge。

### 関節速度飽和

速度上限95%超過量に対する滑らかな二乗ペナルティ。

### 関節トルク飽和

トルク上限95%超過量に対する滑らかな二乗ペナルティ。

### 着地左右差

直近左右の15ms平均着地衝撃差への小さなペナルティ。

## 結果

4.0m/sで、

* 実速度：3.89m/s
* 転倒率：0%
* 滑り：0.39m/s
* 最大衝撃：約2861N
* 周期走行

となりました。

Stage 5と比べると、

* 速度：3.83 → 3.89m/s
* 滑り：0.50 → 0.39m/s
* 最大衝撃：約5321 → 2861N

です。

安全性を上げた結果、速度まで向上しました。

これは以前の方策が、着地衝撃や足滑りでエネルギーを浪費していたことを示唆します。

## 飽和の解釈改善

要約では`joint_v/t=1.00/1.00`と表示されましたが、詳細に見ると、

* 膝速度上限95%以上：約0.9〜1.3%の時間
* 足首トルク上限95%以上：最大約5.3%

でした。

一瞬上限へ触れただけで、継続的に張り付いているわけではありません。

ここでは、**最大比率ではなく上限滞在時間を評価すべき**という教訓が得られました。

# 11. Stage 7：滑り局所解への失敗

Stage 6を4.5m/sへ外挿すると、

* 4.4m/sまでは周期走行
* 4.5m/sでは転倒しないが滑り0.56m/s
* 周期品質が低下

しました。

詳細診断では、支配的な失敗は、

* 速度誤差
* 右足滑り

でした。

そこでStage 7では、

* 70%：4.40〜4.50m/s
* 20%：4.25〜4.55m/s
* 10%：4.50〜4.55m/s

とし、高速時だけ足滑りペナルティを最大-0.05追加しました。

## 結果

4.5m/sで、

* 実速度：4.43m/s
* 転倒率：0%
* 周期数：127
* 衝撃：約2315N

まで改善しました。

しかし滑りは、

```text
Stage 6：0.56m/s
Stage 7：0.71m/s
```

へ悪化しました。

左右別では、

```text
左：0.912m/s
右：0.488m/s
```

という強い非対称性が出ました。

## 原因

学習報酬と評価器の滑り定義を比較した結果、定義差による見かけの問題ではありませんでした。

公式`feet_slide`のraw値も、評価器の滑りも、同じ方向に悪化していました。

Stage 7では高速指令を大量に与えたため、速度追従への圧力が強くなりました。

追加した滑りペナルティは速度報酬に比べて小さく、方策は、

> 左足を大きく滑らせることで速度を稼ぐ

という局所解へ入りました。

この段階で重要だった判断は、Stage 7を追加学習しなかったことです。

Stage 7 checkpointを親にせず、Stage 6へ戻しました。

これは、深層強化学習では「最新版が常に最良」とは限らないことを示しています。

---

# 12. Stage 8：滑り局所解の除去

Stage 8ではStage 6から分岐し直しました。

## 速度分布

```text
80%：4.40〜4.50m/s
20%：4.30〜4.50m/s
4.50m/s超は含めない
```

## 足別excess-slip報酬

単にすべての滑りを罰するのではなく、条件付きで過剰分だけを罰しました。

[
g =
\mathbf{1}[v_{\mathrm{cmd}} \ge 4.40]
\mathbf{1}[e_{xy} \le 0.25]
]

[
c_{\mathrm{slip}}
=================

g\sum_{\mathrm{feet}}
\mathbf{1}[\mathrm{contact}]
\left(
\frac{\max(0,v_{\mathrm{foot},xy}-0.50)}{0.50}
\right)^2
]

weightは-0.20です。

## この設計の意味

速度誤差がまだ大きい状態で滑りを強く罰すると、方策は止まることで滑りをゼロにできます。

そこで、

* まず十分に速度追従している
* 足が接地している
* 足速度が0.50m/sを超えている

場合だけ、超過分を罰しました。

さらに左右足別に計算したため、片足の大滑りを反対足の低滑りで相殺できません。

## 速度報酬のplateau

速度誤差が0.15m/s以内に入った後は、さらに速度を改善する利得を小さくしました。

これは方策に、

> もう十分速いので、これ以上滑って速度を上げるより、品質を改善せよ

と教えるためです。

## 結果

4.5m/sで、

* 実速度：4.369m/s
* 転倒率：0%
* 周期成功率：82%
* 全体滑り：0.425m/s
* 左右滑り：0.492 / 0.352m/s
* 衝撃p95：1994N
* 3500N超過率：0%

となりました。

Stage 7と比較すると、

```text
滑り：0.71 → 0.425m/s
実速度：4.43 → 4.37m/s
```

です。

わずかな速度低下と引き換えに、滑りを大幅に削減できました。

---

# 13. Stage 8から5m/sへの外挿

Stage 8を5.2m/sまで外挿すると、

* 5.0m/s指令：実速度4.88m/s
* 5.1m/s指令：実速度5.00m/s
* 5.2m/s指令：実速度5.06m/s
* 転倒率：すべて0%

でした。

つまり、5m/sを出す能力自体は既に存在していました。

しかし高速度ほど、

* 滑り増加
* 安全周期減少
* 80ms以上の長い飛行増加
* `safe_fires`減少
* 周期分類失敗

が発生しました。

したがって問題は、

> 5m/sを出せないことではなく、5m/sで周期品質を維持できないこと

でした。

---

# 14. Stage 9前の診断：速度誤差の正体

4.7〜5.1m/sで周期が切れる理由を集計すると、主因は速度条件でした。

5.0m/sではprimary resetが、

* 速度追従失敗：240
* 鉛直速度失敗：54
* 飛行不足：11
* 両足着地：1

でした。

同側着地や姿勢失敗は主因ではありません。

## 表示速度と速度誤差が一致しなかった理由

Stage 8、5.0m/sでは、

### episode全体

* yaw-frame前進速度：4.913m/s
* 前進絶対誤差：0.370m/s
* 横速度：0.112m/s
* XY誤差：0.418m/s

### 開始2秒後

* yaw-frame前進速度：5.148m/s
* 前進絶対誤差：0.166m/s
* 横速度：0.108m/s
* XY誤差：0.217m/s

でした。

表示される実速度は、時間平均されたbody-frame前進速度です。

一方、速度誤差は各stepで、

[
|v_{\mathrm{cmd}}-v_t|
]

を計算して平均しています。

一般に、

[
\mathbb{E}[|v_{\mathrm{cmd}}-v_t|]
\neq
|v_{\mathrm{cmd}}-\mathbb{E}[v_t]|
]

です。

さらに、

* 初期加速
* 周期内の速度振動
* 横速度
* body frameとyaw frameの差

も含まれます。

この診断により、5m/s走行そのものが遅いのではなく、硬い速度gateによって良い周期が報酬0になっていることが分かりました。

---

# 15. Stage 9：硬いgateを連続報酬へ変更

## 速度分布

```text
60%：4.85〜5.00m/s
25%：4.70〜4.90m/s
15%：5.00〜5.10m/s
5.20m/s以上なし
```

## 周期報酬の連続化

Stage 8以前は、速度誤差が閾値以内なら成功、外なら0という硬いgateでした。

Stage 9では、

[
q =
\exp\left(
-\left(\frac{e_{\mathrm{forward}}}{0.30}\right)^2
-\left(\frac{e_{\mathrm{lateral}}}{0.20}\right)^2
\right)
]

として、

[
r_{\mathrm{cycle}}
==================

r_{\mathrm{safe\ cycle}}\cdot q
]

に変更しました。

## この変更の意味

少し速度誤差がある場合でも、

* 適切な飛行時間
* 左右交互着地
* 安全な姿勢
* 正常な着地

を完全に0点にしません。

誤差が大きいほど報酬は滑らかに減りますが、正しい周期へ向かう勾配は残ります。

これは高速域では特に重要です。

5m/sでは周期内の瞬間速度変動が大きいため、hard gateでは良い周期も大量に失敗扱いされます。

## 右膝飽和への局所対応

最初のStage 9 pilotでは右膝速度飽和が11.58%まで増えました。

ここでも全関節ペナルティを強化せず、右膝だけを対象にしました。

* 追加weight -0.05：右膝飽和5.89%
* 追加weight -0.10：右膝飽和2.49%

となりました。

問題が発生した関節だけを修正したことで、速度や他関節の余裕を過剰に削らずに済みました。

# 17. なぜこの設計が強く機能したのか

## 17.1 Continuation、あるいはホモトピーとして設計した

最も大きな理由です。

ゼロから5m/sを学習させず、

```text
安定歩行
→ 1.5m/s
→ 2.2m/s
→ 2.5m/s高速歩行
→ 周期走行
→ 4.0m/s
→ 低衝撃4.0m/s
→ 4.5m/s
→ 低滑り4.5m/s
→ 5.0m/s
```

と、毎回近接した問題だけを解かせました。

各Stageでは、前の方策が既に持っている能力をほぼ維持しながら、一つの難しさだけを追加しています。

これは最適化問題として見ると、容易な問題の解を少しずつ難しい問題へ連続的に移す方法です。

---

## 17.2 方策の入出力互換性を維持した

全Stageで、

* 123次元観測
* 37次元行動
* 同じネットワーク構造

を維持しました。

これによりactor、critic、場合によってはoptimizer状態までそのまま再利用できました。

Stageごとにネットワーク構造を変更していたら、これまで学習した制御則を失い、毎回再学習に近くなっていました。

---

## 17.3 速度範囲を広くしすぎなかった

各Stageでは、その時点の限界付近へ分布を集中させました。

例えばStage 3では2.3〜2.6m/s、Stage 8では4.4〜4.5m/sです。

これにより、

* 既にできる低速領域へのサンプル浪費
* まだ不可能な高速領域での大量転倒
* 方策の既存能力の破壊

を避けました。

---

## 17.4 完成報酬だけでなく前駆報酬を使った

Stage 3の失敗から得た最重要知見です。

完成した周期走行だけに報酬を出すと、初期方策では成功イベントが一度も起きず、学習できません。

Stage 4では、

* 離地
* 適切な飛行
* 反対足着地
* 周期継続

へ段階的に報酬を与えました。

これにより、珍しい成功イベントが学習可能な密度へ変わりました。

---

## 17.5 hard gateとcontinuous rewardを使い分けた

品質判定ではhard gateが有用です。

例えば、

* 転倒率5%以下
* 滑り0.55m/s以下
* 周期成功率80%以上

は、成果を明確に評価できます。

しかし学習報酬をすべてhard gateにすると、わずかな失敗で勾配が消えます。

Stage 9では、速度条件を連続的な指数減衰へ変えました。

この使い分けが重要です。

```text
評価：厳しいpass/fail
学習：滑らかな改善方向
```

です。

---

## 17.6 最大値ではなく分布と滞在時間を測った

途中では、

```text
joint_v/t = 1.00 / 1.00
```

や、最大衝撃5000N以上という数字が出ました。

しかし詳細に見ると、

* 上限到達はエピソード時間の約1〜5%
* 衝撃p95は2000N台
* 3500N超過率は1%未満

でした。

最大値だけで判断していたら、不必要に強いペナルティを入れ、走行能力を壊していた可能性があります。

---

## 17.7 悪いcheckpointを捨てた

Stage 7は速度と周期性を改善しましたが、片足滑り0.9m/sを使う局所解へ入りました。

ここで、

> 最新checkpointをさらに学習すれば改善する

とは考えず、Stage 6へ戻りました。

これは非常に重要です。

深層強化学習では学習履歴に強い経路依存性があります。悪い局所解へ入ったcheckpointから報酬を修正しても、その歩容を維持したまま微調整される可能性があります。

そのため、

* 良い親checkpointを保存
* 新Stageを分岐
* 悪ければ破棄
* 良い親から別条件で再分岐

という運用が有効でした。

---

## 17.8 1024環境で希少イベントを探索した

走行への移行では、

* 適切な飛行時間
* 正しい片足着地
* 左右交互
* 姿勢維持
* 速度追従

を偶然同時に満たす必要があります。

1024環境による並列探索は、このような希少イベントを見つける上で有効でした。

ただし、並列数だけでは不十分です。

Stage 3のように報酬が0のままなら、1024環境あっても学習できません。

効果があったのは、

> 大量並列探索と、前駆報酬による成功イベントの増幅

の組み合わせです。

---

# 18. この実験で得た設計原則

今回のプロセスは、次のループとして整理できます。

## 1. まず現在の方策を壊れるところまで評価する

学習前に、外挿によって限界速度を測りました。

## 2. 破綻を一つの指標で判断しない

転倒だけでなく、

* 速度誤差
* 滑り
* 飛行時間
* 周期数
* 左右着地
* 衝撃
* 関節飽和
* 非対称性

へ分解しました。

## 3. 最も支配的な失敗だけを選ぶ

一度に全部直そうとせず、

* Stage 3：疎報酬
* Stage 6：右足下降速度と衝撃
* Stage 8：片足滑り局所解
* Stage 9：速度hard gateと右膝飽和

のように、各段階で主因を一つか二つに絞りました。

## 4. 最小限の報酬変更を行う

変更項目が少なければ、結果との因果関係を追えます。

## 5. 短いpilotで壊れていないか確認する

2環境×1 updateは配線確認だけに使い、性能評価には使いませんでした。

本学習前にも100〜150 iterationsのpilotを挟みました。

## 6. 50エピソード級で評価する

3エピソードの評価は、転倒率が0%、33%、67%と大きく揺れます。

最終的な判断は50エピソードを基準にしました。

## 7. 良いcheckpointだけを次Stageへ渡す

最新ではなく、評価結果が最良のcheckpointを親にしました。

# 19. この成果の正しい位置づけ

今回の結果は、

> G1実機が5m/sで安全に走れる

ことの証明ではありません。

正確には、

> 現在のIsaac Lab上のG1モデル、アクチュエータ設定、接触モデル、摩擦、観測、遅延条件において、5.0m/s指令を高品質に追従する方策を学習した

という成果です。

実機ではさらに、

* action遅延
* センサ遅延
* 状態推定誤差
* モータ熱
* バッテリー電圧
* 構造のたわみ
* 足裏摩擦差
* 地面の微小凹凸
* モデル化されていない接触衝撃

があります。

したがって今後は、

* 摩擦ランダム化
* 質量・重心ランダム化
* PD gainランダム化
* action delay
* センサノイズ
* 外乱
* 不整地

に対するロバスト性評価が必要です。

# 20. 一番重要な結論

この成果を作ったのは、PPOの性能やネットワークサイズだけではありません。

一番効いたのは、

> **失敗を観測可能な物理量へ分解し、方策が現在いる局所解を理解した上で、次の局所解へ移るための最小限の学習信号を与え続けたこと**

です。

特に重要だった転換点は次の三つです。

1. **Stage 4**
   完成報酬だけではなく前駆報酬を導入し、高速歩行から周期走行へ相転移させた。

2. **Stage 8**
   一律の滑りペナルティではなく、速度追従後の足別excess-slipだけを罰し、滑り局所解を除去した。

3. **Stage 9**
   速度hard gateを連続報酬へ変え、5m/sで良い周期への勾配を残した。

最終的には、単に「5m/sを出す方策」ではなく、

> **速度、周期性、滑り、着地衝撃、左右対称性、関節飽和をバランスした走行方策**

へ発展しました。

この設計プロセスは、次のハードル課題でもそのまま使えます。

```text
まず低い固定障害物
→ 越えられない原因を計測
→ 踏切・飛行・着地へ分解
→ 前駆報酬を設計
→ 障害物高さと速度を段階的に拡張
→ 知覚を後から追加
```

今回得た最大の資産は5m/sのcheckpointだけではありません。**失敗を計測し、局所解を診断し、カリキュラムと報酬を段階的に組み替える方法論そのもの**です。
